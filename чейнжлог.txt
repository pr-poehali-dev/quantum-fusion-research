## v2.4 | 2026-06-15 | Фикс: статусы железок в корзине стали индивидуальными для заказа

### Проблема
- У двух заказов с одинаковым ПК (141 и 142) статусы железок в корзине закупки
  «переносились»: смена статуса/приход товара у одного заказа отражались у другого.
- Причина: статус позиции в корзине брался из warehouse_purchase_basket.status —
  одна строка на товар (group_id), общая для всех заказов с этим товаром.

### Решение
- [reserves/basket_by_wip] Статус позиции теперь выводится из
  wip_builds.{slot}_status КОНКРЕТНОЙ сборки (маппинг ready→RECEIVED,
  ordered_transit/delay→ORDERED, иначе NEW). Каждый заказ независим.
- [reserves/sync_order] Убрано глобальное обновление purchase_basket.status
  ='RECEIVED' WHERE group_id — оно переносило статус на все заказы с товаром.
  Статус слота обновляется только у нужной сборки по wb_id.
- [AdminWipTab.updateBasketStatus] Убран вызов глобального basket_status;
  статус пишется только в wip_builds.{slot}_status конкретной сборки.

## v2.3 | 2026-06-15 | Фикс: приёмка поставки гасит минус-резервы и шлёт уведомления

### Проблема
- При приёмке поставки (supply_create) минус-резервы из warehouse_reserves
  НЕ гасились — функция лишь сырым образом списывала qty_negative из supplies.
  Долги без привязки к заказу ("Нет привязки к заказу") игнорировались, в заказ
  не ставились, заказчик не получал уведомления.

### Решение [warehouse/supply_create]
- Приход теперь гасит NEGATIVE-резервы FIFO по дате заказа: переводит их в
  POSITIVE под заказ (по аналогии с reserves.receive_stock), уменьшает буфер,
  кладёт пришедший товар в qty_reserved.
- При гашении заказчику (orders.user_id) создаётся уведомление в notifications
  ("Товар поступил и зарезервирован под ваш заказ №...").
- Погашенные заказы попадают в negative_alerts (показываются в модалке приёмки).
- Остаток прихода дочищает «сиротские» qty_negative-долги (рассинхрон без
  записи в резервах).

## v1.9 | 2026-06-15 | Фикс: архив товаров показывал "пусто"

### Проблема
- Вкладка "Архив" в товарах всегда показывала "Архив пуст", хотя в БД были
  архивные товары (is_archived=true).
- Причина: backend products row_to_product НЕ возвращал поле is_archived,
  поэтому фронт-фильтр .filter(p => p.is_archived) отсекал все строки.

### Решение
- [products] В SELECT добавлено p.is_archived, в row_to_product добавлено
  поле "is_archived" (row[18]). Теперь архив отображается корректно.

- [reserves/tests.json] Добавлен финальный тест cleanup_selftest — чистка

### Бизнес-логика (по требованию заказчика)
- При отмене/удалении заказа: заказанное у поставщика железо (статус ORDERED)
  ОСТАЁТСЯ в закупке — приедет и упадёт в наличие. Снимается только не заказанное (NEW).

### Изменения
- [builds] cancel_order переписан: вместо ручного SQL теперь использует
  warehouse_core.release_order_reserves(only_new_negative=True).
  ИСПРАВЛЕН БАГ: раньше корзина закупки (warehouse_purchase_basket) не уменьшалась
  при отмене — теперь вызывается basket_reduce. Раньше снималось даже заказанное
  железо — теперь ORDERED бережётся.
- [builds] Создан backend/builds/warehouse_core.py (release_order_reserves + basket_reduce).
- [warehouse] delete_wip переписан на тот же release_order_reserves(only_new_negative=True).
  ИСПРАВЛЕН БАГ: раньше не обновлял orders.status и pc_builds.status — теперь
  заказ → archived, сборка → archive. Корзина обрабатывается единообразно.
- [warehouse] Создан backend/warehouse/warehouse_core.py (+ поддержка supply_id=NULL).
- [wip-builds] DELETE и cancel_order: only_new_negative изменён False→True
  (заказанное железо больше не снимается). ⚠️ НЕ задеплоено: sync_backend не деплоит
  эту функцию (видит nodejs22, таймаут). Применится при ручном деплое.
- [структура.txt] Исправлена прошлая ошибка: папка wip-builds НЕ мёртвая, а рабочая
  (URL cb6e9d4e-...). Добавлено описание единого ядра резервов в 4 функциях.

### Технические детали
- Три реализации отмены/удаления теперь ведут себя одинаково.
