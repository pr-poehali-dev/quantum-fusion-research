## Функции и их назначение

### auth
Аутентификация: регистрация, вход, управление сессиями.
Хеширует пароли, генерирует токены сессий.

### products
Управление товарами/компонентами конфигуратора.
CRUD товаров, слоты конфигуратора, отслеживание остатков.

### builds
Сборки ПК: создание, редактирование, статусы, фото, цены, теги.
PATCH actions: generate_client_link, claim, set_tags.
POST action cancel_order — отмена WIP-заказа. Использует общий
warehouse_core.release_order_reserves(only_new_negative=True):
- POSITIVE резервы → возврат товара в наличие (qty+, qty_reserved-)
- NEGATIVE резервы → снимаются ТОЛЬКО если корзина в статусе NEW;
  заказанное у поставщика (ORDERED) остаётся в закупке и придёт в наличие
- корзина закупки уменьшается через basket_reduce
- заказ → status='archived', pc_build → 'archive', wip_build удаляется
Файл backend/builds/warehouse_core.py — копия ядра (release_order_reserves, basket_reduce).

### warehouse
Склад: группы товаров, поставки, магазины, движения, инвентаризация.
POST action delete_wip — удаление WIP-сборки. Использует общий
warehouse_core.release_order_reserves(only_new_negative=True) — та же логика что в builds:
снимает резервы, бережёт заказанное (ORDERED), уменьшает корзину, архивирует заказ и сборку.
Файл backend/warehouse/warehouse_core.py — копия ядра.
Таблицы: warehouse_groups, warehouse_supplies, warehouse_stores,
warehouse_movements, warehouse_reserves, warehouse_purchase_basket,
warehouse_stock_log, warehouse_backorders.

### НДС / скидка / предоплата (v3.13)
- warehouse.supply_create: обязательный has_vat (да/нет); менеджер вводит
  price_with_vat, в заход пишется cost_price = price_with_vat×(1−скидка%).
- warehouse action=settings (GET) / settings_set (POST) — глобальные настройки
  в таблице app_settings (purchase_discount_percent и др.).
- builds: pc_builds.sell_with_vat. Если TRUE — цена продажи на фронте
  = (железо+сборка)×1.22, округление вверх до 250 ₽.
- wip-builds: orders.prepayment_percent (def 30) / prepayment_amount.
  SELECT отдаёт remaining_amount (остаток = total − предоплата). PATCH
  принимает prepayment_percent ИЛИ prepayment_amount (пересчёт второго).
- orders: GET одиночного заказа отдаёт prepayment_*; PUT action=set_prepayment
  (по % или сумме). Общий UI-компонент src/components/admin/PrepaymentEditor.
- Клиентская страница сборки (BuildPreview) показывает предоплату и остаток
  «К доплате» (данные из wip-builds по token/order_id), только для
  ПОДТВЕРЖДЁННОЙ предоплаты (prepayment_confirmed_amount).

### Счета сотрудников + подтверждение предоплаты (v3.15)
- Таблицы: employee_accounts (баланс), employee_account_tx (история).
  orders.prepayment_confirmed. finance_transactions +employee_id/+order_id.
- schedule.employee_create: автосоздание счёта сотрудника.
- finance: GET accounts (сотрудники+баланс), account_log; POST credit_account
  (ручное +/−), confirm_prepayment (приход «Предоплата» + опц. на счёт
  сотрудника + orders.prepayment_confirmed=TRUE).
- Переход WIP «Согласование→Заказ» требует модалку подтверждения предоплаты
  (PrepaymentConfirmModal): сумма + назначение (касса/сотрудник).
- FinanceTab: карточка кассы раскрывается в список счетов сотрудников.
- Таблицы: app_settings, +поля в warehouse_supplies (has_vat, price_with_vat),
  pc_builds (sell_with_vat), orders (prepayment_percent, prepayment_amount).

### Счета зачисления + предоплата/оплата остатка (v3.27)
- Таблицы: cash_accounts (касса/Авито/терминал — баланс, code, color),
  cash_account_tx (история). finance_transactions +cash_account_id.
  orders.remaining_paid / remaining_paid_amount.
- finance: GET cash_accounts, cash_account_log. POST confirm_prepayment И
  confirm_remaining (action) принимают cash_account_id ИЛИ employee_id —
  деньги идут на денежный счёт (касса/Авито/терминал) или счёт сотрудника.
  Описание операций: «Предоплата за заказ #N» / «Оплата заказа #N» (+order_id).
  get_log отдаёт order_id (для гиперссылки на /admin/order/N).
- orders: GET одиночного заказа отдаёт prepayment_confirmed, remaining_paid,
  remaining_paid_amount. Выдача (PATCH done / writeoff_order) блокируется,
  если remaining_paid=FALSE → {error:"remaining_unpaid"}.
- wip-builds: переход «Забрали» блокируется без оплаты остатка
  (error remaining_unpaid). «Согласование→Заказ» по-прежнему требует предоплату.
- Frontend: PrepaymentConfirmModal — выбор счёта (касса/Авито/терминал/сотрудник)
  + mode "prepayment"/"remaining". OrderProcessPage: кнопка «Внести предоплату»
  (пока prepayment_confirmed=false), окно оплаты остатка перед выдачей.
  AdminWipTab: при «Забрали» без оплаты остатка открывает окно оплаты.
  FinanceTab: карточка кассы раскрывается в «Счета зачисления» + счета сотрудников;
  в логе движений ссылка на заказ.

### Маржа сборки + сборщик ПК (v3.24)
- employees.assembler_percent (% за сборку, в карточке сотрудника),
  wip_builds.assembled_by (сборщик), orders.assembler_paid (защита от задвоения).
- wip-builds action=margin (id|order_id): разбивка маржи по компонентам
  (pc_builds.price − себестоимость из warehouse_reserves) + total_margin.
- Кнопка 🤑 в WIP → WipMarginModal. Модалка «Ред.» WIP (WipEditModal) с
  выбором сборщика (employees из schedule). Строка «Сборщик» в таблице.
- orders PATCH→done: для pc_build обязателен assembled_by (иначе 400),
  начисляет % сотрудника × total на employee_accounts + employee_account_tx.
- changeStage: переход в «Забрали» переводит заказ в done (и начисляет).

### finance
Раздел «Финансы» (вкладка /admin/finance, FinanceTab.tsx).
GET action=summary — сводка: стоимость склада (закупка/продажа),
маржа за текущий месяц отдельно по pc_build и parts (с avg_margin,
revenue, count), нал в кассе. Маржа = orders.total − себестоимость
из партий (warehouse_reserves POSITIVE FULFILLED/ACTIVE × cost_price).
GET action=log — единый лог: финансовые транзакции + продажи (done-заказы).
GET action=types — типы операций.
POST action=add_tx — добавить операцию (kind: income/expense/collection).
  collection (инкассация в офис) → affects_pnl=FALSE, уменьшает кассу,
  не считается расходом компании.
POST action=add_type — новый тип. DELETE del_tx / del_type.
Таблицы: finance_types, finance_transactions.

### НДС-заход + авторасход офиса + баланс офиса (v3.18)
- warehouse.supply_create: НДС-товар → cost_price = price_with_vat ×
  (1 − purchase_discount_percent/100) (поставщик даёт скидку по ставке),
  обычный → cost_price = введённая цена. vat_percent — справочная ставка.
- Авто-расход «Закупка товара» считает и пишет ТОЛЬКО функция finance
  (action=sync_supply_expense): сумма за день+магазин = Σ cost_price ×
  (qty+qty_reserved+qty_negative). warehouse после приёмки/правки дёргает
  finance по HTTP (notify_finance_supply_expense). У склада нет колонки
  updated_at в finance_transactions — не использовать её там.
- (устар. v3.18) Авто-расход офиса при приходе: ОДНО событие «Расходы на товары» на
  день+магазин (finance_transactions.auto_supply=TRUE, store_id, expense_date,
  supply_count), сумма наращивается = Σ cost_price×qty поставок дня.
- warehouse settings/settings_set: чтение/запись app_settings (whitelist:
  purchase_discount_percent, default_prepayment_percent, vat_percent).
  UI: «Настройки закупки» в WarehouseTab (НДС% + скидка).
- finance summary.office: { balance, income (приходы+инкассация), expense,
  supply_expense (закупка товара), other_expense }. FinanceTab — блок
  «Баланс офиса» с отдельными суммами.

### orders
Заказы: создание с привязкой к пользователю, список, смена статусов.
Статусы: new (по умолчанию при создании), done, archived, cancelled.
cancelled/archived считаются "мёртвыми" — приёмка игнорирует их резервы.

### reserves
HTTP-обёртка над ядром складских резервов (warehouse_core.py).
Управление резервированием: POSITIVE (товар в наличии) и NEGATIVE (под заказ).
Корзина закупки, диагностика остатков.
Эндпоинты: reserve_order, release_order, recalc_order, receive (приёмка+FIFO),
basket, basket_status, basket_by_wip, diag, stock_log.
GET ?action=selftest — встроенный селф-тест складской логики (12 кейсов,
работает на временных данных с откатом, ничего не сохраняет). Ответ содержит
summary {passed/failed/failed_cases}. Запускать после правок складской логики.
ВАЖНО: приёмка (receive_stock) гасит минус-резервы FIFO, но ПРОПУСКАЕТ заказы
в статусе cancelled/archived — их товар уходит в свободное наличие.

### rma
Гарантийные случаи (рекламации): создание, смена статусов,
перевод товаров в карантин, возврат/замена.

### tags
CRUD тегов для сборок ПК. Простая справочная таблица.

### comments
Комментарии к сборкам и статьям. Управление по сессиям.

### articles
Статьи и тесты: CRUD, категории, публикация, slugи.

### notifications
Уведомления пользователей: получение непрочитанных, смена статуса.
(Известная проблема с 401 вынесена в чейнжлог как открытая задача.)

### upload
Загрузка изображений: сжатие в WebP, оптимизация, сохранение в S3.
Принимает base64 в JSON (не multipart).

### generate-warranty
Генерация PDF гарантийных сертификатов. Поддержка кириллицы.

### telegram-auth
Привязка Telegram аккаунта: генерация кодов подтверждения.

### schedule
Расписание сотрудников. Требует прав администратора.

### b2b-prices
B2B прайс-лист для партнёров (розница + опт). ПУБЛИЧНЫЙ доступ без авторизации
аккаунта: список товаров (название, партномер part_number, sku, категория,
наличие) виден всем. Цены (retail/opt1/opt2) отдаются ТОЛЬКО при верном пароле
в заголовке X-B2B-Password (секрет B2B_PASSWORD).
GET / — список (+ has_prices). GET /?action=check_password — проверка пароля {ok}.
Поиск (?search=) ищет по name + part_number + sku.
Фронт: src/pages/B2B.tsx — пароль сохраняется в localStorage (b2b_password),
повторный вход пропускается. Колонка «Партномер» правее названия.

### cables
Конфигуратор кастомных кабелей: CRUD, клиентские ссылки.

### sync-products
Синхронизация товаров из внешних API. Импорт/экспорт Excel (base64).

### crm-probe
Тестовый зонд для проверки внешнего CRM API. Служебная функция.
