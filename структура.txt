## Промокоды и акции (v7.06)
- backend/promos (URL .../b70b011e-6249-4d99-8b90-f0f695e62cae) — система скидок
  в корзине + публичные акции для сайта + CRUD для админки.
  Actions:
    • GET / (или public) — публичные активные акции (is_public) для сайта.
    • POST validate — проверка кода и расчёт скидки в корзине
      (body: code, items[], total, customer_phone?; user_id по X-Session-Id).

    • GET products_search&q= — поиск для типа «Конкретный товар»: товары
      (kind=product) + готовые сборки ПК (kind=build, id="build:<id>") (v7.31,
      сборки добавлены v7.37).

      публичным product-акциям (для бейджа «Акция» на карточках товаров И сборок
      витрины) (v7.31; builds добавлены v7.38).

      ссылками url) для страницы /promo/:id (v7.38).

  активаций) вместо сырого used_count (v7.31).

## Маркетинг и аналитика источников (v6.80)
- backend/marketing (URL .../1683aaf5-e13f-4ef7-9848-9ca2ecf03b8a) — источники
  клиентов, группы источников, помесячные рекламные бюджеты и сводная аналитика.
  Actions: groups / group_save / group_archive; sources (active=true) /
  source_save; budgets (group_id) / budget_save (upsert по group_id+месяц);
  analytics (from/to) → KPI, by_source, by_group (CPL/CAC/ROMI), timeline.
  Лиды = max(ручные лиды бюджета, заявки квиза, заказы) по группе.
  sales_report (from/to) [v7.25] → отчёт продаж для закупок. Продажа = позиции
  ВЫДАННЫХ заказов (status='done', разбор orders.items JSONB через
  jsonb_array_elements). По каждой позиции: продано шт, выручка, ср.цена,
  себестоимость (avg по партиям склада; fallback — avg по всем партиям для
  распроданных), маржа ₽/%, остаток, дневной спрос, дней-до-нуля (остаток÷
  спрос), дефицит под спрос на 30 дней, авто-метки (хит/хорошая маржа/низкая
  маржа/скоро закончится/нет в наличии/дозаказать).
  [v7.26] Тип спроса (demand_type): различает реальный спрос и разовые продажи
  по ЧАСТОТЕ — orders_cnt (в скольких разных заказах) + distinct_days.
  «регулярный» (≥2 заказов и ≥2 дней, либо ≥3) / «разовый» (1 заказ —
  вероятно случайность) / «нет данных». Дневной спрос, дефицит и метки
  хит/скоро закончится/дозаказать — ТОЛЬКО для регулярного спроса; разовые
  помечаются «разовая продажа». totals += regular/one_off. Промпт для ИИ
  копируется без CSV (CSV отдельной кнопкой).
  [v7.27] +блок spec_groups: контроль остатков по ТИПУ комплектующего через
  характеристики совместимости. Группируем по атрибутам spec_attributes с
  affects_compat=true (select/multiselect): значение из product_spec_values.value
  + разворот value_json (multiselect) через jsonb_array_elements_text. По
  каждому (категория, характеристика, значение): товаров в группе, суммарный
  остаток (ВСЕ товары типа), продано всего/регулярно, спрос по регулярным,
  дней-хватит, дефицит, warning (нет в наличии/скоро закончится/дозаказать).
  totals += spec_warnings. Фронт SalesReport: блок «Контроль по характеристикам»
  (предупреждения по типам + таблица), второй CSV «by_specs».

## Цены сборок ПК — единый механизм (v6.37)
- pc_builds.lock_prices (V0176): FALSE (по умолч.) = цены комплектующих
  синхронизируются со складом (актуальная products.price); TRUE = цены
  зафиксированы (используется components.price, правится вручную в админке).
- backend/builds.fmt_build подставляет в каждый компонент current_price:
  при lock_prices=FALSE — актуальную цену каталога (_get_price_map, 1 запрос),
  при TRUE — зафиксированную price. Все читатели (сайт+админка) считают
  ЕДИНООБРАЗНО: sum((current_price ?? price) * qty) + assembly_fee, затем НДС
  (sell_with_vat → +22%, округление вверх до 250 ₽).
- Точки расчёта: BuildPreview (страница сборки), Builds/HomeStonks (карточки),
  AdminCatalogTab (редактор, compPrice + чекбокс «Фиксировать цены»),
  BuildsList (список админки, withVat).

## Приёмка по счёту через локальную LLM / OCR (v5.81)
- backend/receipt-scan (URL .../de7a55a6-...) — приёмка товара по фото счёта.
  Очередь распознавания + матчинг позиций с товарами склада.
  Actions:
    • worker_pull / worker_result — для воркера на сервере с GPU (X-Worker-Token,
      секрет RECEIPT_WORKER_TOKEN). Воркер сам забирает NEW-задачи и возвращает JSON.
    • create_job / job_status — фронт создаёт задачу (image_url из S3) и опрашивает.
    • jobs_status (POST, job_ids[]) — пакетный статус нескольких задач ОДНИМ
      запросом (экономия вызовов при batch-приёмке нескольких файлов).
    • draft_save / draft_get / drafts_open / draft_close — черновики листа приёмки
      (чтобы не терять прогресс при создании нового SKU). drafts_open отдаёт
      total (полное число OPEN-листов) + до 200 листов.
    • drafts_close_all (POST) — закрыть ВСЕ открытые листы одним UPDATE (CANCELED).
    • remember_match — память ручных сопоставлений; rematch — пересчёт матчинга.
  ЭКОНОМИЯ ВЫЗОВОВ: одиночный опрос статуса — бэкофф (первый через 10с, далее
    10→15→20с, не дёргает при свёрнутой вкладке). BATCH (2-20 счетов): счета
    обрабатываются ПО ОЧЕРЕДИ (следующий отправляется после готовности
    предыдущего, активна максимум одна задача), опрос — бэкофф 10→15→20с через
    jobs_status. 20 счетов ≈ 50 вызовов receipt-scan вместо ~76.
  matcher.py — нормализация + нечёткое сравнение (артикул→память→fuzzy), без либ.
- БД: receipt_jobs, receipt_drafts, receipt_match_memory (V0174).
- Фронт: src/components/admin/ReceiptScanModal.tsx — загрузка фото, опрос статуса,
  экран сверки (🟢/🟡/🔴), приёмка партий (supply_create). Интеграция в
  WarehouseTab: кнопка «Принять по счёту», бейдж/панель незаконченных листов,
  возврат к черновику после создания нового товара. api.receiptScan.* + upload.receipt.
- воркер-сервер/worker.py + ИНСТРУКЦИЯ.txt — локальный FastAPI/Ollama-воркер
  (модель qwen2-vl:7b), НЕ часть деплоя, ставится на сервер пользователя.

## Оптимизация изображений (v6.20-6.21)
- backend/img-optimize (URL .../f8ab2fb6-...) — сжимает картинку по URL в WebP
  в размерах 480/768/1024 (для srcset) и кладёт в S3 в optimized/ с длинным кешем.
  Python+Pillow. Режимы:

### stress (НОВОЕ)
Стресс-тесты железа от desktop-приложения StressRunner (C#/.NET, папка desktop/StressRunner).

### price-monitor
Мониторинг цен парсером + автонаценка + утренний обзор предложений.
Цель: парсер шлёт ТОЛЬКО изменения цен (HTTP POST), система матчит с нашими
товарами и предлагает менеджеру обновить цены (подтверждение вручную).
Два контура доступа в одной функции:
1) ПАРСЕР: POST с заголовком X-Parser-Token == секрет PARSER_INGEST_TOKEN.
   action=ingest. Тело: {source, items:[{name,price,sku,url,in_stock}]}.
   Кладёт в price_observations, матчит по названию (коэф. Жаккара над токенами,
   порог 0.45), формирует price_suggestions:
   - есть наш товар → kind='price_change'
   - товара нет → kind='new_product'
   Рекомендованная цена = цена_конкурента * 0.93 (-7%), округл. до 250 ₽.
   Дубли по товару не плодятся: существующее 'new' предложение обновляется.
   После ingest шлётся Telegram-сводка (падение/рост цен, новые товары) через
   tg_notify.py — только если реально есть изменения (тихий прогон = без спама).
2) АДМИН: X-Admin-Token == ADMIN_KEY (или X-Session-Id с ролью admin).
   GET ?action=list&kind=price_change|new_product — список 'new' + counts
       (+ ext_sku, match_score).
   GET ?action=match&id=NN (или &q=название) — кандидаты каталога с % похожести.
   POST action=link_product {id, product_id} — привязать new_product к товару.
   POST action=accept {id, final_price?, with_vat?, product_id?} — принять:
        ручная цена / suggested_price, НДС (+22%, округл. вверх до 250).
        ВАЖНО (v7.24): у price-monitor НЕТ прав на складские таблицы, поэтому
        сама функция обновляет только products.price и статус предложения
        (accepted), а warehouse-сторону (price_retail, история цен, пересчёт
        сборок) делегирует функции warehouse через HTTP action=price_sync
        {product_id, price_retail}. accept обёрнут в try/except (при сбое 500),
        accept_all — поштучный commit.
   POST action=reject {id} — отклонить. POST action=accept_all — принять все price_change.
Таблицы: price_sources, price_observations, price_suggestions (миграция V0154).
Frontend: вкладка /admin/price_monitor (PriceMonitorTab) в группе «Операции».
   Кнопка «Обработать» открывает модалку ProcessModal (цена, НДС, матчинг+привязка).
API: api.priceMonitor.list/accept/reject/acceptAll/match/linkProduct (src/lib/api.ts).
Секреты: PARSER_INGEST_TOKEN — токен парсера; PRICE_ALERT_CHAT_ID (опц.) — чат
   Telegram для сводок (иначе TELEGRAM_MANAGER_CHAT_ID).

CRUD товаров, слоты конфигуратора, отслеживание остатков.
БРЕНДЫ (v4.40): таблица brands + products.brand_id (nullable). resource=brands —
CRUD справочника (GET/POST/PUT/DELETE; DELETE отвязывает товары brand_id=NULL).
Товары и слоты отдают brand_id + brand (имя). Слоты конфигуратора берут НАСТОЯЩИЙ
бренд из brands (раньше ошибочно подставлялась категория).
КАСКАДНЫЙ ПЕРЕСЧЁТ СБОРОК (v3.98): при PUT (изменение цены товара) функция
_recalc_builds_for_product обновляет цены всех ПРОДАЖНЫХ сборок с этим товаром
(components[].price, parts_total, total_price; +22% НДС если sell_with_vat).
НЕ трогает наличие (in_stock=TRUE) и архив (status='archive').
_apply_vat — общая формула цены с НДС (ceil(base*1.22/250)*250).
ТИР-ЛИСТЫ (v4.60): resource=tier. GET — все НЕархивные товары с фото (можно ?category=slug),
поля tier_rank (S/A/B/C/D/F или null) + tier_pos (порядок в ряду) + категории.
POST/PUT — сохранение расстановки items=[{id,tier_rank,tier_pos}]. Поля в products
(миграция V0148). Фронт: /tier-lists (src/pages/TierLists.tsx), drag&drop для админа.

### builds
Сборки ПК: создание, редактирование, статусы, фото, цены, теги.
PATCH actions: generate_client_link, claim, set_tags.
POST action cancel_order — отмена WIP-заказа. Использует общий
warehouse_core.release_order_reserves(only_new_negative=True):
- POSITIVE резервы → возврат товара в наличие (qty+, qty_reserved-)
- NEGATIVE резервы → снимаются ТОЛЬКО если корзина в статусе NEW;
  заказанное у поставщика (ORDERED) остаётся в закупке и придёт в наличие
- корзина закупки уменьшается через basket_reduce
- заказ → status='archived', pc_build → 'archive', wip_build удаляется
Файл backend/builds/warehouse_core.py — копия ядра (release_order_reserves, basket_reduce).

### warehouse
Склад: группы товаров, поставки, магазины, движения, инвентаризация.
POST action delete_wip — удаление WIP-сборки. Использует общий
warehouse_core.release_order_reserves(only_new_negative=True) — та же логика что в builds:
снимает резервы, бережёт заказанное (ORDERED), уменьшает корзину, архивирует заказ и сборку.
Файл backend/warehouse/warehouse_core.py — копия ядра.
КАСКАДНЫЙ ПЕРЕСЧЁТ СБОРОК (v3.98): group_update с price_retail синхронизирует
products.price И вызывает warehouse_core.recalc_builds_for_product — пересчёт
цен продажных сборок (как в products PUT). Наличие/архив не трогаются.
Таблицы: warehouse_groups, warehouse_supplies, warehouse_stores,
warehouse_movements, warehouse_reserves, warehouse_purchase_basket,
warehouse_stock_log, warehouse_backorders.

### Совместимость комплектующих / конфигуратор (v4.30 → v4.31 DATA-DRIVEN)
Цель: гибкий конструктор характеристик железа, расширяемый без правок кода.
Конфигуратор по этим данным подбирает совместимое (переработка конфигуратора — позже).

DATA-DRIVEN модель (V0141–V0143), 4 таблицы:
- spec_categories — типы железа (code/name/icon/color/product_category_slug/sort).
  product_category_slug привязывает к categories.slug — авто-определение типа товара.
- spec_attributes — поля категории (code/name/field_type[select|multiselect|number|
  bool|text]/options(jsonb)/unit/affects_compat/is_required/sort/applies_to). affects_compat —
  можно использовать в связях; иначе «для ознакомления». is_required — для статуса.
  applies_to (v4.66, 'all'|'air'|'liquid') — управляющий тип охлаждения: поле видно
  только при выбранном cooler_type (Воздушное→air / СЖО→liquid). Фильтрация в
  редакторе значений, фильтрах (ShopFilters/SlotPickerModal) и совместимости.
  Хелпер фронта src/lib/coolingFilter.ts.
- product_spec_values — значения у товара (product_id, attribute_id, value/value_json).
  UNIQUE(product_id, attribute_id). value_json — для multiselect.
- spec_links — карта связей: from_attribute_id, to_attribute_id, rule
  (eq|lte|gte|contains), is_active. Стартовые правила: сокет CPU=плата, тип памяти
  RAM=плата=CPU, длина GPU<=корпус, высота кулера<=корпус, сокет CPU∈кулер,
  форм-фактор платы∈корпус, форм-фактор БП=корпус.

[v7.42] СИНХРОНИЗАЦИЯ склада (warehouse action=recalc_reserves, кнопка
«Синхронизация» на вкладке Склад): приводит партии к эталону по warehouse_reserves.
Шаг 0 — закрывает ACTIVE-резервы на done/cancelled (FULFILLED/RELEASED). Далее по
каждой партии: physical = qty + qty_reserved; qty_reserved := min(want_pos,
physical); qty := physical - qty_reserved (>=0). Излишек POSITIVE над физикой
конвертируется в NEGATIVE-резервы (POSITIVE→NEGATIVE в warehouse_reserves) →
