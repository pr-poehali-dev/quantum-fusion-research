## Функции и их назначение

### stress (НОВОЕ)
Стресс-тесты железа от desktop-приложения StressRunner (C#/.NET, папка desktop/StressRunner).
Цель: приложение на ПК запускает по списку внешние программы/скрипты, каждый на
своё время, собирает код завершения + длительность + файлы-отчёты, шлёт на сайт.
Два контура:
1) EXE-приём: POST X-Stress-Token == секрет STRESS_INGEST_TOKEN, action=ingest.
   Тело: {run_uid, profile_name, machine_name, os_info, note, started_at, finished_at,
   status, results:[{test_name,command,exit_code,duration_sec,planned_sec,timed_out,
   success,started_at,finished_at,files:[{name,content_base64}]}]}.
   Идемпотентность по run_uid. Файлы-отчёты base64 → S3 (stress_reports/), CDN url.
2) АДМИН: X-Admin-Token == ADMIN_KEY (или X-Session-Id роли admin).
   GET action=list — список прогонов; GET action=get&id — прогон с результатами+файлами;
   DELETE action=delete_run&id — удалить прогон.
ПРОФИЛИ ТЕСТОВ (редактор без JSON):
- Таблица stress_profiles (name/note/tests jsonb/is_active/sort_order, миграция V0156).
- Админ: GET profiles_list, POST/PUT profile_save, DELETE profile_delete.
- EXE: GET profiles_pull (по X-Stress-Token) — только активные профили.
- Приложение тянет профили с сайта (при старте + пункт меню), кэширует в profiles.json.
Таблицы: stress_runs, stress_results, stress_files (V0155), stress_profiles (V0156).
Frontend: вкладка /admin/stress (StressTestsTab) в группе «Прочее»:
  переключатель «Результаты / Профили тестов» (StressProfilesTab — редактор кнопками).
API: api.stress.list/get/deleteRun/profilesList/profileSave/profileDelete (src/lib/api.ts).
Секрет STRESS_INGEST_TOKEN — токен приложения для приёма данных.
УВЕДОМЛЕНИЯ: action=notify (по токену) → tg_notify.notify_stress в Telegram
  (секрет STRESS_TG_CHAT_ID). События: test_failed (при ошибке теста сразу,
  прогон не падает) и run_finished (всегда). Шлёт Uploader.NotifyAsync из Runner.
Desktop-приложение (НЕ часть веб-сборки): desktop/StressRunner — собирается в .exe
через `dotnet publish` на ПК (инструкция в README.md). Локальная БД SQLite на ПК.
  Тип: WPF-окно (net8.0-windows, тёмная тема как на сайте), стиль OCCT.
  Файлы: App.xaml(+cs), MainWindow.xaml(+cs), Theme.xaml, Runner.cs (движок,
    колбэки OnLog/OnTestStart/OnTestDone), HwInfoReader.cs (сенсоры HWiNFO из
    реестра VSB — график CPU/GPU нагрузки и температур), Uploader.cs, Storage.cs,
    Models.cs, ConsoleMode (Program.cs) — пакетный режим run "профиль".
  Два режима: окно (по умолчанию) и пакетный `StressRunner.exe run "Профиль"`.
  Для графика нужен HWiNFO с включённым Shared Memory Support / Gadget.
  ПОРТАТИВНАЯ сборка: один .exe (PublishSingleFile+SelfContained). Батник
    Собрать_EXE.bat создаёт чистую папку StressRunner_App: StressRunner.exe +
    StressTests\ (утилиты) + Others\ (settings/profiles/БД, авто-создаётся).
    Paths.cs разрешает относительные пути (StressTests\OCCT\OCCT.exe) от корня —
    переносится на флешке на любой ПК. Пресеты в админке дают такие пути.
  АВТОРИЗАЦИЯ: в окне кнопка «🔑 Авторизоваться» (AuthWindow) — ключ + имя ПК,
    проверка через stress?action=verify_token, сохранение в Others\settings.json,
    авто-перезапуск. Бейдж «✓ Админ-режим включён · ПК: …».
  ТЕМЫ (как на сайте): ThemeManager + ThemeWindow (кнопка 🎨) — тёмная/светлая +
    6 акцентов. Theme.xaml на DynamicResource (смена на лету). Кастомный ComboBox.
  ДАТЧИКИ: LibreHardwareMonitor (HardwareMonitor.cs) — НАПРЯМУЮ, без HWiNFO.
    ReadAll() → {Hardware,Name,Type,Unit,Value}. HwInfoReader — обёртка
    (Read/IsAvailable/Debug). MetricsCollector сэмплит раз/сек за прогон →
    min/max/avg по Temperature/Load/Fan/Clock/Power (RunPayload.Metrics).
    DebugWindow (кнопка «🔍 Датчики (отладка)») — список датчиков.
    Требуются права администратора (есть в манифесте).
  Таблица stress_metrics (V0157). backend: ingest сохраняет, get_run отдаёт.
    Админка: плитки min/сред/max в карточке прогона (StressTestsTab).
  НАСТРОЙКИ МЕТРИК: таблица stress_metric_prefs (V0158), actions metric_prefs_list/
    metric_prefs_save. Вкладка «Метрики» (MetricPrefsTab): скрыть/показать,
    порядок (drag), своё имя, категория. Применяется в карточке прогона +
    фильтр по категориям. metricUtils.ts (categoryOf/prefId/CATEGORIES).
    Двойной клик по плитке метрики → переход на «Метрики» + красная подсветка.
  ПРЕСЕТЫ ТЕСТОВ: таблица stress_test_presets (V0159), actions presets_list/
    preset_save/preset_delete. Кнопка «Создать новый тест» — конструктор пресета
    (форма). Пресеты из БД используются в редакторе профиля. Cinebench R23 засеян.
  АВТОНАЖАТИЕ КЛАВИШ: KeySender (Win32) — поле send_keys в тесте (FurMark «P»).
  OCCT 12+ CLI в пресетах: -run -test=CPU -duration=600 -auto=1 -report=...

## Функции и их назначение (продолжение)

### price-monitor
Мониторинг цен парсером + автонаценка + утренний обзор предложений.
Цель: парсер шлёт ТОЛЬКО изменения цен (HTTP POST), система матчит с нашими
товарами и предлагает менеджеру обновить цены (подтверждение вручную).
Два контура доступа в одной функции:
1) ПАРСЕР: POST с заголовком X-Parser-Token == секрет PARSER_INGEST_TOKEN.
   action=ingest. Тело: {source, items:[{name,price,sku,url,in_stock}]}.
   Кладёт в price_observations, матчит по названию (коэф. Жаккара над токенами,
   порог 0.45), формирует price_suggestions:
   - есть наш товар → kind='price_change'
   - товара нет → kind='new_product'
   Рекомендованная цена = цена_конкурента * 0.93 (-7%), округл. до 250 ₽.
   Дубли по товару не плодятся: существующее 'new' предложение обновляется.
2) АДМИН: X-Admin-Token == ADMIN_KEY (или X-Session-Id с ролью admin).
   GET ?action=list&kind=price_change|new_product — список 'new' + counts.
   POST action=accept {id} — принять: проставить suggested_price в products.price.
   POST action=reject {id} — отклонить. POST action=accept_all — принять все price_change.
Таблицы: price_sources, price_observations, price_suggestions (миграция V0154).
Frontend: вкладка /admin/price_monitor (PriceMonitorTab) в группе «Операции».
API: api.priceMonitor.list/accept/reject/acceptAll (src/lib/api.ts).
Секрет PARSER_INGEST_TOKEN — токен парсера для авторизации входящих данных.

### sn-archive
Реестр серийных номеров (SnArhive). Связь серийник -> товар -> поставка -> магазин.
Цель: знать, откуда КОНКРЕТНО куплена железка (особенно процессоры) — для гарантийки.
Actions: list_serials (поиск/фильтры q/category/store_id/status), lookup (магазин по SN),
add_serials (массово к поставке; магазин берётся из поставки), update_serial, delete_serial,
categories / category_add / category_remove (какие категории требуют SN при приёмке), stores.
Таблицы: sn_archive, sn_categories. Стартовая категория учёта — «Процессоры».
Frontend: вкладка /admin/sn_archive (SnArchiveTab), окно ввода SN при приёмке (WarehouseTab).
generate-warranty подставляет магазин по SN из sn_archive (фолбэк — последняя поставка товара).

### auth
Аутентификация: регистрация, вход, управление сессиями.
Хеширует пароли, генерирует токены сессий.

### products
Управление товарами/компонентами конфигуратора.
CRUD товаров, слоты конфигуратора, отслеживание остатков.
БРЕНДЫ (v4.40): таблица brands + products.brand_id (nullable). resource=brands —
CRUD справочника (GET/POST/PUT/DELETE; DELETE отвязывает товары brand_id=NULL).
Товары и слоты отдают brand_id + brand (имя). Слоты конфигуратора берут НАСТОЯЩИЙ
бренд из brands (раньше ошибочно подставлялась категория).
КАСКАДНЫЙ ПЕРЕСЧЁТ СБОРОК (v3.98): при PUT (изменение цены товара) функция
_recalc_builds_for_product обновляет цены всех ПРОДАЖНЫХ сборок с этим товаром
(components[].price, parts_total, total_price; +22% НДС если sell_with_vat).
НЕ трогает наличие (in_stock=TRUE) и архив (status='archive').
_apply_vat — общая формула цены с НДС (ceil(base*1.22/250)*250).
ТИР-ЛИСТЫ (v4.60): resource=tier. GET — все НЕархивные товары с фото (можно ?category=slug),
поля tier_rank (S/A/B/C/D/F или null) + tier_pos (порядок в ряду) + категории.
POST/PUT — сохранение расстановки items=[{id,tier_rank,tier_pos}]. Поля в products
(миграция V0148). Фронт: /tier-lists (src/pages/TierLists.tsx), drag&drop для админа.

### builds
Сборки ПК: создание, редактирование, статусы, фото, цены, теги.
PATCH actions: generate_client_link, claim, set_tags.
POST action cancel_order — отмена WIP-заказа. Использует общий
warehouse_core.release_order_reserves(only_new_negative=True):
- POSITIVE резервы → возврат товара в наличие (qty+, qty_reserved-)
- NEGATIVE резервы → снимаются ТОЛЬКО если корзина в статусе NEW;
  заказанное у поставщика (ORDERED) остаётся в закупке и придёт в наличие
- корзина закупки уменьшается через basket_reduce
- заказ → status='archived', pc_build → 'archive', wip_build удаляется
Файл backend/builds/warehouse_core.py — копия ядра (release_order_reserves, basket_reduce).

### warehouse
Склад: группы товаров, поставки, магазины, движения, инвентаризация.
POST action delete_wip — удаление WIP-сборки. Использует общий
warehouse_core.release_order_reserves(only_new_negative=True) — та же логика что в builds:
снимает резервы, бережёт заказанное (ORDERED), уменьшает корзину, архивирует заказ и сборку.
Файл backend/warehouse/warehouse_core.py — копия ядра.
КАСКАДНЫЙ ПЕРЕСЧЁТ СБОРОК (v3.98): group_update с price_retail синхронизирует
products.price И вызывает warehouse_core.recalc_builds_for_product — пересчёт
цен продажных сборок (как в products PUT). Наличие/архив не трогаются.
Таблицы: warehouse_groups, warehouse_supplies, warehouse_stores,
warehouse_movements, warehouse_reserves, warehouse_purchase_basket,
warehouse_stock_log, warehouse_backorders.

### Совместимость комплектующих / конфигуратор (v4.30 → v4.31 DATA-DRIVEN)
Цель: гибкий конструктор характеристик железа, расширяемый без правок кода.
Конфигуратор по этим данным подбирает совместимое (переработка конфигуратора — позже).

DATA-DRIVEN модель (V0141–V0143), 4 таблицы:
- spec_categories — типы железа (code/name/icon/color/product_category_slug/sort).
  product_category_slug привязывает к categories.slug — авто-определение типа товара.
- spec_attributes — поля категории (code/name/field_type[select|multiselect|number|
  bool|text]/options(jsonb)/unit/affects_compat/is_required/sort/applies_to). affects_compat —
  можно использовать в связях; иначе «для ознакомления». is_required — для статуса.
  applies_to (v4.66, 'all'|'air'|'liquid') — управляющий тип охлаждения: поле видно
  только при выбранном cooler_type (Воздушное→air / СЖО→liquid). Фильтрация в
  редакторе значений, фильтрах (ShopFilters/SlotPickerModal) и совместимости.
  Хелпер фронта src/lib/coolingFilter.ts.
- product_spec_values — значения у товара (product_id, attribute_id, value/value_json).
  UNIQUE(product_id, attribute_id). value_json — для multiselect.
- spec_links — карта связей: from_attribute_id, to_attribute_id, rule
  (eq|lte|gte|contains), is_active. Стартовые правила: сокет CPU=плата, тип памяти
  RAM=плата=CPU, длина GPU<=корпус, высота кулера<=корпус, сокет CPU∈кулер,
  форм-фактор платы∈корпус, форм-фактор БП=корпус.

warehouse actions (DATA-DRIVEN):
- spec_schema (GET) — категории+атрибуты+связи разом.
- spec_cat_create/update/delete, spec_attr_create/update/delete,
  spec_link_create/update/delete (CRUD конструктора).
- spec_products (GET) — все железки + статус новый/готов (по is_required атрибутам
  категории, привязанной через product_category_slug).
- spec_values_get/spec_values_save — значения характеристик товара.
api.warehouse.specSchema/specCat*/specAttr*/specLink*/specProducts/specValues*.

Мастер характеристик товара (v5.66): src/components/admin/ProductSpecWizard.tsx —
пошаговый мастер в форме ГРУППЫ СКЛАДА (WarehouseTab → GroupModal). Категория
группы выбирается из списка категорий каталога (id/name/slug); по slug мастер
берёт атрибуты (spec_schema, по product_category_slug), по одному шагу на
характеристику (select/multiselect/number/bool/text). Значения автопривязываются
к товару группы (warehouse_groups.product_id): spec_values_save после
group_create (product_id в ответе) / group_update; при редактировании
подгружаются через spec_values_get. group_create принимает category_id.
Доп. атрибуты (V0166): серия, цвет, тип накопителя (SSD/HDD), форм-фактор
накопителя — описательные, affects_compat=false.

СТАРАЯ модель (product_specs, V0140) — оставлена, но фронт переведён на новую.
warehouse group_create по-прежнему вызывает ensure_product_specs (product_specs).

Frontend: вкладка /admin/compatibility (CompatibilityTab) справа от «Товары».
3 подвкладки (src/components/admin/compatibility/):
- ProductsValues («Железки») — таблица товаров, фильтры (категория/статус/поиск),
  динамический редактор значений по схеме категории, статус новый/готов.
- AttributesBuilder («Характеристики») — конструктор: слева категории компонентов,
  справа их поля. Модалки категории (иконка/цвет/привязка к категории товаров) и
  характеристики (тип поля/варианты/единица/влияет на совместимость/обязательная).
- LinksMap («Карта связей») — SVG-граф категорий по кругу + список правил,
  модалка создания правила (выбор 2 характеристик с affects_compat + тип правила).

### НДС / скидка / предоплата (v3.13)
- warehouse.supply_create: обязательный has_vat (да/нет); менеджер вводит

- warehouse action=settings (GET) / settings_set (POST) — глобальные настройки
  в таблице app_settings (purchase_discount_percent и др.).
- builds: pc_builds.sell_with_vat. Если TRUE — цена продажи на фронте
  = (железо+сборка)×1.22, округление вверх до 250 ₽.

аккаунта: список товаров (название, партномер part_number, sku, категория,
наличие) виден всем. Цены (retail/opt1/opt2) отдаются ТОЛЬКО при верном пароле
в заголовке X-B2B-Password (секрет B2B_PASSWORD).
GET / — список (+ has_prices). GET /?action=check_password — проверка пароля {ok}.
Поиск (?search=) ищет по name + part_number + sku.
Фронт: src/pages/B2B.tsx — пароль сохраняется в localStorage (b2b_password),
повторный вход пропускается. Колонка «Партномер» правее названия.

### cables
Конфигуратор кастомных кабелей: CRUD, клиентские ссылки.

### sync-products
Синхронизация товаров из внешних API. Импорт/экспорт Excel (base64).

### crm-probe
