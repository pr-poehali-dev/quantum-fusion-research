# ТЗ: Парсер цен (DNS, Ozon, расширяемый) + интеграция с BeGraphics

Документ для разработки в Cursor. Цель — сделать **локальный парсер** цен на
комплектующие ПК (DNS, Ozon, с возможностью добавлять новые источники), который
отправляет данные в уже готовый облачный эндпоинт сайта. Максимально экономим
облачное время: **вся тяжёлая работа (краулинг, парсинг HTML, матчинг) — на
локальной машине**, облако только принимает готовый JSON и пишет в БД одним
быстрым запросом.

---

## 0. Что УЖЕ готово на стороне сайта (не переделывать, использовать)

- **Облачная функция `price-monitor`** (Python):
  `https://functions.poehali.dev/505d6a55-4cdb-4d30-9e46-3292ad49b4ab`
  - Приём данных парсера: `POST` с заголовком `X-Parser-Token: <PARSER_INGEST_TOKEN>`,
    тело `{ "source": "...", "items": [...] }`, `action=ingest`.
  - Матчинг присланных позиций с нашим каталогом `products` по названию
    (Jaccard-токены, порог 0.45), запись в `price_observations`, формирование
    `price_suggestions` (`kind='price_change'` или `'new_product'`).
  - Рекомендованная цена = `цена_источника * 0.93`, округление до 250 ₽.
  - Админ-контур: `GET ?action=list&kind=...`, `POST accept/reject/accept_all`.
- **Таблицы БД:** `price_sources`, `price_observations`, `price_suggestions`.
- **UI админки:** `src/components/admin/PriceMonitorTab.tsx` — вкладка «Мониторинг цен».
- **Образец UX матчинга с % похожести:** приёмка по счёту
  `src/components/admin/ReceiptScanModal.tsx` + `backend/receipt-scan` (matcher.py).

> **Важно про цену «меняется везде»:** итоговая цена товара на сайте берётся так:
> `CASE WHEN warehouse_groups.price_retail > 0 THEN price_retail ELSE products.price END`.
> Значит при применении новой продажной цены надо обновлять И `products.price`,
> И `warehouse_groups.price_retail` (если у товара есть складская группа), иначе
> группа перекроет новую цену. Это учтено в разделе 3 (доработка backend).

## ЧАСТЬ A. ЛОКАЛЬНЫЙ ПАРСЕР (новый проект, отдельный репозиторий/папка)

### A1. Стек и запуск
- Python 3.11+, библиотеки: `httpx` (или `requests`), `selectolax`/`beautifulsoup4`,
  `playwright` (только для сайтов с JS, включать по флагу источника), `pydantic`.
- Запуск: `python run.py` вручную или по расписанию (cron / Планировщик Windows).
- Конфиг в `.env`: `INGEST_URL`, `PARSER_INGEST_TOKEN` (тот же секрет, что в облаке).

### A2. Расширяемая архитектура источников
Каждый источник — отдельный модуль-«адаптер» с единым интерфейсом. Добавление
нового сайта = добавить один файл-адаптер + запись в конфиг. Обязательные адаптеры
на старте: **DNS** и **Ozon** (категории комплектующих для ПК).

```
parser/
  run.py                 # точка входа: читает конфиг, гоняет адаптеры, шлёт в облако
  config.yaml            # список источников и что парсить (см. A3)
  core/
    base.py              # BaseAdapter: parse() -> list[Item]
    sender.py            # отправка батчами в price-monitor (см. A4)
    models.py            # pydantic-модель Item
    dedup.py             # локальный кэш последних цен (не слать неизменившееся)
  adapters/
    dns.py               # адаптер DNS
    ozon.py              # адаптер Ozon
    generic.py           # универсальный адаптер по CSS-селекторам из конфига
```

Единая модель позиции (`Item`):
```python
class Item(BaseModel):
    name: str            # наименование как на сайте источника
    price: float         # цена, ₽ (число, без пробелов/₽)
    url: str             # прямая ссылка на карточку товара (гиперссылка для менеджера)
    sku: str | None = None
    in_stock: bool | None = None
```

### A3. Конфиг источников (`config.yaml`) — расширяемость «добавлять можно было»
```yaml
sources:
  - name: "DNS"
    adapter: dns
    enabled: true
    categories:                 # разделы комплектующих ПК
      - "https://www.dns-shop.ru/catalog/.../videokarty/"
      - "https://www.dns-shop.ru/catalog/.../processory/"
    max_pages: 5                # ограничение глубины (экономия)
  - name: "Ozon"
    adapter: ozon
    enabled: true
    categories:
      - "https://www.ozon.ru/category/videokarty-15721/"
    max_pages: 5
  # Новый источник добавляется так (универсальный адаптер по селекторам):
  - name: "Регард"
    adapter: generic
    enabled: false
    categories: ["https://..."]
    selectors:
      card: ".product-card"
      name: ".product-card__name"
      price: ".product-card__price"
      url: "a.product-card__link@href"
      in_stock: ".in-stock"     # наличие: есть элемент = в наличии
```
Менеджер/разработчик добавляет источник правкой `config.yaml` (для типовых сайтов
через `generic` — вообще без кода).

### A4. Отправка в облако — ЭКОНОМИЯ облачного времени (обязательно)
- Слать **батчами** (например по 200–500 позиций в одном POST), а НЕ по одной.
  Одна облачная функция обрабатывает весь батч за один вызов.
- Перед отправкой применять **локальный дедуп** (`dedup.py`): хранить в локальном
  файле/SQLite последнюю отправленную цену по (source, url). Если цена и наличие
  не изменились с прошлого прогона — **не отправлять** эту позицию. Это резко
  снижает и число вызовов, и объём работы облака.
- Ретраи с бэкоффом при сетевых ошибках; таймаут запроса 30 c.
- Заголовки: `Content-Type: application/json`, `X-Parser-Token: <token>`.
- Тело:
  ```json
  {
    "source": "DNS",
    "items": [
      {"name": "Видеокарта Gigabyte RTX 4070", "price": 54990, "url": "https://...", "sku": "123", "in_stock": true}
    ]
  }
  ```
- Ответ: `{ "ok": true, "processed": N, "price_changes": X, "new_products": Y }`.

### A5. Этика/устойчивость парсинга
- User-Agent как у браузера, пауза 1–3 с между запросами, соблюдать `robots`.
- Playwright включать только для источников, где без JS не отдаётся цена
  (флаг `render_js: true` в конфиге источника). По умолчанию — лёгкий HTTP-парсинг.
- Логи в файл: сколько собрано/отправлено/пропущено дедупом по каждому источнику.

## ЧАСТЬ B. ДОРАБОТКИ НА СТОРОНЕ САЙТА (в этом проекте)

### B1. Telegram-уведомления о новых товарах и изменениях цен
Дублировать в Telegram каждое НОВОЕ предложение из `ingest`.
- В `backend/price-monitor/index.py`, в `_ingest(...)`: после формирования
  `price_suggestions` собрать созданные/обновлённые предложения и отправить
  **одно сводное сообщение** в Telegram (не по одному — экономия и читаемость).
- Использовать существующий механизм отправки (см. `backend/tg-bot` / `backend/notifications`;
  взять оттуда способ вызова Telegram Bot API и chat_id из секретов).
- Секреты: `TELEGRAM_BOT_TOKEN` (проверить, есть ли уже), `PRICE_ALERT_CHAT_ID`.
- Формат сообщения (сводка за батч):
  ```
  🟡 Мониторинг цен — источник DNS
  Изменения цен: 3 | Новые товары: 5

  💰 Изменения:
  • RTX 4070 Gigabyte: наша 50 000 → рынок 54 990 (реком. 51 000) [ссылка]
  ...
  🆕 Новые товары:
  • RTX 4080 Palit — 89 990 ₽ [ссылка]
  ...
  Открыть в админке: /admin (вкладка «Мониторинг цен»)
  ```
- Ошибка отправки в Telegram НЕ должна валить `ingest` (обернуть в try/except).

### B2. UI карточки предложения (`PriceMonitorTab.tsx`) — доработать под требования
Для КАЖДОГО предложения показать:
- **Наименование** (ext_name — как у источника).
- **Цена** источника (market_price).
- **Переключатель «с НДС / без НДС»** (влияет на расчёт итоговой цены, см. B4).
- **Источник с гиперссылкой** (ext_url открывается в новой вкладке).
- Кнопка **«Обработать»**.

Для `new_product` дополнительно — **привязка к товару из нашей базы с % похожести**
(как в приёмке по счёту `ReceiptScanModal`):
- Поле поиска по каталогу `products` + список кандидатов, отсортированный по
  проценту совпадения названия (переиспользовать подход/матчер из приёмки).
- Можно выбрать существующий товар (тогда предложение станет как `price_change`
  для него) или оставить как новый.

### B3. Экран «Обработать» — установка продажной цены
После нажатия «Обработать» показать блок:
- Заголовок: **«Изменить продажную цену на …»**
- Поле ввода цены, **предзаполненное округлённой** рекомендованной ценой
  (округление вверх до кратного 250: …000/250/500/750). Менеджер может отредактировать.
- Кнопка **ОК** — применяет цену.
- Если выбран режим «с НДС» — предустановленная цена считается с учётом НДС
  (та же формула проекта: `ceil(base * 1.22 / 250) * 250`), но менеджер всё равно
  может поправить вручную.

### B4. Применение цены — «меняется везде» (сборки + каталог)
Доработать `action=accept` (и `accept_all`) в `backend/price-monitor`:
- Принимать из тела **итоговую цену от менеджера** (`final_price`) вместо слепого
  использования `suggested_price` (менеджер мог отредактировать).
- Для товара `product_id`:
  1. `UPDATE products SET price = final_price WHERE id = product_id`.
  2. Если у товара есть складская группа (`products.warehouse_group_id`):
     `UPDATE warehouse_groups SET price_retail = final_price WHERE id = <group_id>`
     — иначе группа перекроет цену на витрине (см. правило `CASE` в products GET).
  3. Записать в `warehouse_price_history` (как делает warehouse при смене цены),
     чтобы история цен не рвалась.
- Пометить предложение `status='accepted', decided_at=now()`.
- В результате новая цена автоматически применяется:
  - в каталоге и на карточке товара (`products` GET);
  - в сборках, у которых цены НЕ зафиксированы (`pc_builds.lock_prices=false`),
    т.к. они считают по актуальной `current_price` из каталога (уже реализовано).
- Обновить `src/lib/api.ts` (`api.priceMonitor.accept`) — передавать `final_price`
  и `with_vat`.

### B5. НДС-логика (уточнение)
- `with_vat=true`: итоговая цена = округл. вверх до 250 от `base * 1.22`.
- `with_vat=false`: итоговая цена = округл. вверх до 250 от `base`.
- `base` по умолчанию = рекомендованная (market_price * 0.93). Менеджер правит поле руками.

## ЧАСТЬ D. Критерии приёмки
1. Локальный парсер собирает цены DNS и Ozon по категориям комплектующих ПК и
   успешно отправляет батч в `price-monitor` (`ok:true`, корректные счётчики).
2. Новый источник добавляется правкой `config.yaml` (для типового сайта — без кода).
3. Дедуп: при повторном прогоне без изменений цен отправляется ≈0 позиций.
4. В админке (вкладка «Мониторинг цен») появляются «Изменения цен» и «Новые товары».
5. По каждому предложению в Telegram приходит сводное уведомление.
6. Для нового товара можно выбрать товар из базы с % похожести (как в приёмке).
7. «Обработать» → поле с округлённой ценой (250/500/750/000), редактируется,
   переключатель НДС работает.
8. После «ОК» продажная цена меняется и отражается в каталоге, на карточке товара
   и в сборках (незафиксированных) — одинаково.
9. Облачное время минимально: парсинг локально, облако вызывается только на батч-приём
   и на применение цены менеджером.
