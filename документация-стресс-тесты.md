# Контракт интеграции: Stress-Test EXE ↔ Сайт

Документ для разработки **desktop EXE-приложения** (его делает Cursor).
Часть на стороне сайта (cloud-функция + админка) уже реализована и описана здесь
как готовый контракт. EXE обязан строго следовать этим форматам.

> **Роли:** EXE пишет Cursor. Сайт (backend `stress` + админ-панель) веду я.
> Любое изменение контракта согласуется с обеими сторонами.

---

## 0. Общая архитектура

```
┌─────────────────────────┐         HTTPS (JSON)          ┌──────────────────────┐
│  EXE StressRunner (C#)   │  ───────────────────────────> │  Cloud-функция stress │
│  на тестовом ПК          │  <─────────────────────────── │  (Python, poehali)    │
└─────────────────────────┘     X-Stress-Token (auth)      └──────────┬───────────┘
                                                                       │
                                                            пишет в PostgreSQL
                                                            + файлы в S3
                                                            + Telegram-уведомления
                                                                       │
                                                            ┌──────────▼───────────┐
                                                            │  Админка сайта        │
                                                            │  (просмотр прогонов,  │
                                                            │   профили тестов)     │
                                                            └──────────────────────┘
```

- EXE **только исходящие** HTTPS-запросы. Белый IP / проброс портов НЕ нужны.
- EXE **тянет** профили тестов с сайта и **отгружает** результаты на сайт.
- Профили тестов редактируются в админке сайта, EXE их скачивает (`profiles_pull`).

## 1. Эндпоинт и авторизация

**Базовый URL функции:**
```
https://functions.poehali.dev/ffa7efcd-7a92-4a76-a463-abec515d846c
```

Все запросы EXE идут на этот URL, action передаётся в query: `?action=...`.

**Авторизация EXE — заголовок:**
```
X-Stress-Token: <значение секрета STRESS_INGEST_TOKEN>
```
- Токен задаётся в админке сайта (секрет `STRESS_INGEST_TOKEN`) и вводится в настройках EXE.
- Если токен неверный/отсутствует → HTTP **403** `{"error": "forbidden"}`.
- Перед сохранением токена в конфиг EXE должен проверить его через `verify_token`.

**CORS / заголовки запроса:**
```
Content-Type: application/json
X-Stress-Token: <token>
```

> ⚠️ EXE использует ТОЛЬКО 4 action'а: `verify_token`, `profiles_pull`, `ingest`, `notify`.
> Остальные action'ы (`list`, `get`, `delete_run`, управление профилями) — админские,
> EXE их НЕ вызывает.

---

## 2. Action: `verify_token` (проверка ключа)

Вызывается при вводе токена в настройках EXE, чтобы убедиться, что ключ верный.

**Запрос:**
```
GET /?action=verify_token
Headers: X-Stress-Token: <token>
```

**Ответ 200:**
```json
{ "ok": true, "valid": true }
```
**Ответ 403** (неверный токен): `{ "error": "forbidden" }`

---

## 3. Action: `profiles_pull` (скачать профили тестов)

EXE при запуске / по кнопке «Обновить профили» тянет актуальный список тестов с сайта.

**Запрос:**
```
GET /?action=profiles_pull
Headers: X-Stress-Token: <token>
```

**Ответ 200:**
```json
{
  "profiles": [
    {
      "name": "Профиль 1 — Prime95",
      "note": "Проверка CPU на стабильность",
      "tests": [
        {
          "name": "Prime95 — Torture Test",
          "program": "StressTests\\prime95\\prime95.exe",
          "args": "-t",
          "working_dir": "",
          "duration_sec": 900,
          "timeout_is_success": true,
          "success_exit_code": 0,
          "report_files": ["StressTests\\prime95\\results.txt"],
          "min_run_sec": 30,
          "send_keys": "",
          "send_keys_delay_sec": 5
        }
      ]
    }
  ]
}
```

Возвращаются только **активные** профили (`is_active = true`), в порядке `sort_order`.

### Поля одного теста (`tests[]`) — что EXE обязан понимать:

| Поле                  | Тип     | Назначение |
|-----------------------|---------|------------|
| `name`                | string  | Имя теста (для логов и отчёта) |
| `program`             | string  | Путь к exe-приложению теста (относительный или абсолютный) |
| `args`                | string  | Аргументы командной строки |
| `working_dir`         | string  | Рабочая папка ("" = папка program) |
| `duration_sec`        | number  | Сколько секунд держать тест запущенным |
| `timeout_is_success`  | boolean | Если true: завершение по таймауту = успех (тест «крутится бесконечно», глушим по времени) |
| `success_exit_code`   | number  | Код выхода, считающийся успехом (обычно 0) |
| `report_files`        | string[]| Список путей к файлам-отчётам, которые надо собрать после теста |
| `min_run_sec`         | number  | Минимальное время работы; если процесс упал раньше — это провал |
| `send_keys`           | string  | Клавиши, которые надо «нажать» в окне теста (для автозапуска внутри GUI) |
| `send_keys_delay_sec` | number  | Задержка перед отправкой клавиш |

> EXE сам реализует логику: запуск program с args в working_dir, ожидание duration_sec,
> отправку send_keys (если задано), сбор report_files, вычисление success.

## 4. Action: `ingest` (отгрузка результатов прогона)

Главный эндпоинт. После завершения прогона EXE отправляет ВСЕ результаты одним POST.

**Запрос:**
```
POST /?action=ingest
Headers: X-Stress-Token: <token>, Content-Type: application/json
```

**Тело запроса:**
```json
{
  "run_uid": "f3a9c1b2-...-uuid",
  "profile_name": "Профиль 1 — Prime95",
  "machine_name": "PC-TEST-01",
  "os_info": "Windows 11 Pro 23H2 (build 22631)",
  "note": "Проверка после замены термопасты",
  "started_at": "2026-06-27T10:30:00Z",
  "finished_at": "2026-06-27T11:45:30Z",

  "results": [
    {
      "test_name": "Prime95 — Torture Test",
      "command": "StressTests\\prime95\\prime95.exe -t",
      "exit_code": 0,
      "duration_sec": 905.5,
      "planned_sec": 900,
      "timed_out": false,
      "success": true,
      "started_at": "2026-06-27T10:30:00Z",
      "finished_at": "2026-06-27T10:45:05Z",
      "files": [
        { "name": "results.txt", "content_base64": "<BASE64>" }
      ]
    }
  ],

  "metrics": [
    {
      "key": "cpu_package_temp",
      "label": "CPU Package Temperature",
      "unit": "°C",
      "min": 35.5,
      "max": 89.2,
      "avg": 72.1,
      "samples": 540
    }
  ]
}
```

### Поля верхнего уровня

| Поле           | Тип    | Обяз. | Описание |
|----------------|--------|-------|----------|
| `run_uid`      | string | ДА    | Уникальный ID прогона (GUID). Гарантия идемпотентности — см. ниже |
| `profile_name` | string | ДА    | Имя профиля, по которому шёл прогон |
| `machine_name` | string | ДА    | Имя ПК |
| `os_info`      | string | нет   | Версия ОС |
| `note`         | string | нет   | Комментарий пользователя |
| `started_at`   | ISO8601| нет   | Время начала прогона (UTC, формат `2026-06-27T10:30:00Z`) |
| `finished_at`  | ISO8601| нет   | Время конца прогона |
| `results`      | array  | ДА    | Результаты по каждому тесту |
| `metrics`      | array  | нет   | Сводные метрики мониторинга (HWiNFO/LibreHardwareMonitor) |

### Поля одного результата (`results[]`)

| Поле          | Тип            | Описание |
|---------------|----------------|----------|
| `test_name`   | string         | Имя теста (как в профиле) |
| `command`     | string         | Реально выполненная команда (program + args) |
| `exit_code`   | number \| null | Код выхода процесса (null если не дождались/убили) |
| `duration_sec`| number         | Фактическая длительность в секундах (дробное допустимо) |
| `planned_sec` | number         | Плановая длительность (= `duration_sec` из профиля) |
| `timed_out`   | boolean        | Был ли тест остановлен по таймауту |
| `success`     | boolean        | Итог теста. EXE вычисляет сам (см. правило ниже) |
| `started_at`  | ISO8601        | Старт теста |
| `finished_at` | ISO8601        | Финиш теста |
| `files`       | array          | Файлы-отчёты. `name` + `content_base64` (содержимое файла в base64) |

**Правило вычисления `success` (на стороне EXE):**
```
success = true, если:
   (timeout_is_success && timed_out)               // тест-«крутилка», заглушён по времени = ОК
   ИЛИ (exit_code == success_exit_code && duration_sec >= min_run_sec)
иначе success = false
```

### Поля одной метрики (`metrics[]`)

| Поле       | Тип    | Описание |
|------------|--------|----------|
| `key`      | string | Машинный ключ (`cpu_package_temp`, `gpu_hotspot`, `gpu_usage`, ...) |
| `label`    | string | Человекочитаемое имя |
| `unit`     | string | Единица (`°C`, `%`, `об/мин`, `W`, `MHz`) |
| `min`      | number | Минимум за прогон |
| `max`      | number | Максимум за прогон |
| `avg`      | number | Среднее за прогон |
| `samples`  | number | Кол-во замеров |

> Метрики — сводные ПО ПРОГОНУ (агрегаты), а не временной ряд. EXE сам собирает
> поток показаний (через HWiNFO shared memory / LHM) и считает min/max/avg/samples.

### Ответ `ingest`

**Успех (200):**
```json
{ "ok": true, "run_id": 42, "results": 5, "metrics": 8 }
```
**Повторная отправка того же `run_uid` (200, идемпотентность):**
```json
{ "ok": true, "duplicate": true, "run_id": 42 }
```
**Ошибка авторизации (403):** `{ "error": "forbidden" }`

> ⚠️ **Идемпотентность:** при сетевых сбоях EXE МОЖЕТ безопасно повторить `ingest`
> с тем же `run_uid` — дубликат прогона создан не будет, вернётся существующий `run_id`.
> Поэтому `run_uid` генерируется ОДИН раз на старте прогона и не меняется при ретраях.

### Загрузка файлов
- Файлы передаются ВНУТРИ JSON как `content_base64` (НЕ multipart).
- Backend сам декодирует, кладёт в S3 (`stress_reports/`), сохраняет CDN-URL.
- Рекомендация: не слать гигантские файлы. Логи/txt-отчёты — норм. Если отчёт
  большой (>5–10 МБ) — обрезать или архивировать на стороне EXE.

## 5. Action: `notify` (мгновенные уведомления в Telegram)

EXE может слать события в реальном времени (не дожидаясь конца прогона):
упал тест / завершился прогон. Сайт пересылает их в Telegram менеджерам.

**Запрос:**
```
POST /?action=notify
Headers: X-Stress-Token: <token>, Content-Type: application/json
```

**Событие «тест упал»:**
```json
{
  "event": "test_failed",
  "machine": "PC-TEST-01",
  "profile": "Профиль 1 — Prime95",
  "test_name": "Prime95 — Torture Test",
  "exit_code": 1,
  "duration_sec": 45.2
}
```

**Событие «прогон завершён»:**
```json
{
  "event": "run_finished",
  "machine": "PC-TEST-01",
  "profile": "Профиль 1 — Prime95",
  "passed": 4,
  "total": 5
}
```

**Ответ:** `{ "ok": true }` (всегда 200, даже если Telegram недоступен — не блокирует EXE).

> `notify` — необязательный, «лучшее-усилие». Основной источник правды — `ingest`.

## 6. Жизненный цикл прогона (рекомендуемый сценарий EXE)

```
1. Старт EXE → verify_token (если в конфиге есть токен)
2. profiles_pull → показать пользователю список профилей
3. Пользователь выбирает профиль → жмёт «Запустить»
4. EXE генерирует run_uid (GUID), фиксирует started_at
5. (опц.) запускает мониторинг HWiNFO/LHM в фоне → копит метрики
6. Для каждого test в профиле по порядку:
     - запустить program с args в working_dir
     - (опц.) отправить send_keys через send_keys_delay_sec
     - ждать duration_sec ИЛИ выхода процесса
     - заглушить процесс, собрать report_files (base64)
     - вычислить success
     - (опц.) при провале → notify(event=test_failed)
7. finished_at, агрегировать метрики (min/max/avg/samples)
8. ingest(весь прогон) — с ретраями при сетевых ошибках (тот же run_uid)
9. (опц.) notify(event=run_finished)
```

## 7. Зависимости и окружение EXE (рекомендации для Cursor)

- **Платформа:** Windows 10/11 x64. .NET 8 (C#) — рекомендуется (self-contained single-file exe).
- **HTTP:** `HttpClient` + System.Text.Json. Таймаут запроса `ingest` — щедрый (60–120 c),
  файлы в base64 могут раздуть тело.
- **Мониторинг датчиков:** LibreHardwareMonitorLib (NuGet) или чтение HWiNFO Shared Memory.
  Считать поток значений → агрегировать в min/max/avg/samples.
- **Автоввод клавиш:** для `send_keys` — WinAPI `SendInput` / `PostMessage` (надёжнее, чем SendKeys).
- **Конфиг:** хранить URL функции, X-Stress-Token, имя ПК. Токен — не светить в логах.
- **Идемпотентность/ретраи:** очередь неотправленных прогонов на диске; повтор `ingest`
  с тем же `run_uid` до успеха.
- **Время:** все даты — UTC в ISO8601 с `Z` (`DateTime.UtcNow.ToString("yyyy-MM-ddTHH:mm:ssZ")`).

## 8. Что сделано на стороне сайта (НЕ трогает Cursor)

- Cloud-функция `stress` со всеми action'ами (`ingest/profiles_pull/verify_token/notify`
  для EXE; `list/get/delete_run` + CRUD профилей — для админки).
- Таблицы БД: `stress_runs`, `stress_results`, `stress_metrics`, `stress_files`, `stress_profiles`.
- Загрузка файлов-отчётов в S3, ссылки в CDN.
- Telegram-уведомления (секреты `TELEGRAM_BOT_TOKEN`, `STRESS_TG_CHAT_ID`).
- Админка: список прогонов, карточка прогона (тесты + метрики + файлы), редактор профилей.

### Схема таблиц (справочно, для понимания, что приедет в БД)

**stress_runs** — шапка прогона
`id, run_uid, profile_name, machine_name, os_info, note, started_at, finished_at,
total_tests, passed_tests, failed_tests, status (completed|partial), created_at`

**stress_results** — результат одного теста
`id, run_id, test_name, command, exit_code, duration_sec, planned_sec, timed_out,
success, started_at, finished_at, sort_order, created_at`

**stress_metrics** — агрегаты мониторинга
`id, run_id, key, label, unit, min_val, max_val, avg_val, samples`

**stress_files** — файлы-отчёты теста
`id, result_id, file_name, file_url (CDN), file_size, created_at`

**stress_profiles** — профили тестов (источник для profiles_pull)
`id, name, note, tests (jsonb), is_active, sort_order, created_at, updated_at`

## 9. Чек-лист согласования (что подтвердить перед стартом разработки EXE)

- [ ] Cursor реализует именно эти 4 action'а и эти точные имена полей JSON.
- [ ] `run_uid` — GUID, один на прогон, неизменен при ретраях.
- [ ] Даты — UTC ISO8601 с `Z`.
- [ ] Файлы — base64 внутри JSON `results[].files[]`, не multipart.
- [ ] `success` считается по правилу из §4.
- [ ] Метрики — агрегаты (min/max/avg/samples), не временной ряд.
- [ ] Токен берётся из секрета `STRESS_INGEST_TOKEN` (выдаёт владелец сайта).

> Если Cursor предложит изменить любое поле/формат — он должен прислать diff контракта,
> я обновлю backend и эту документацию синхронно.
