# ТЗ: ИИ-агент для работы со сборками (AI Build Agent)

> Документ для разработки внешнего воркера в Cursor.
> Версия ТЗ: v0.1 (черновик, дорабатывается).
> Проект: BeGraphics — интернет-магазин по сборке ПК.
> Стек проекта: React (Vite) + Python 3.11 Cloud Functions + PostgreSQL + S3.

---

## 0. Что делаем (в одном абзаце)

Отдельный сервис-воркер («ИИ-агент»), который по входящему тексту (заявка с сайта,
свободный текст ТЗ или голосовое сообщение из Telegram) собирает готовый конфиг ПК:
подбирает совместимые комплектующие из **актуального пула склада**, учитывает
**бюджет** и **режим приоритета** (маржа / наличие / соответствие ТЗ), проверяет
совместимость и возвращает черновик сборки в формате основного проекта. Менеджер
принимает/правит черновик; правки копятся как примеры и улучшают качество подбора
(RAG, без переобучения весов).

## 1. Архитектурная роль воркера

```
┌────────────┐   заявка/текст/голос    ┌──────────────────┐
│  Основной  │ ──────────────────────► │   ИИ-АГЕНТ        │
│  проект    │                         │  (этот воркер)   │
│ (сайт/бот/ │ ◄────────────────────── │                  │
│  админка)  │   черновик сборки JSON   └───────┬──────────┘
└────────────┘                                  │
       ▲                                         │ читает пул железа,
       │ сохранение сборки,                      │ наличие, маржу,
       │ фидбек менеджера                        ▼ совместимость, примеры
       │                              ┌──────────────────────┐
       └──────────────────────────── │ PostgreSQL (та же БД) │
                                      └──────────────────────┘
```

Воркер — это HTTP-сервис (можно как Cloud Function проекта `backend/ai-build`,
можно как отдельный контейнер). Он:
1. Ходит в ту же PostgreSQL (read-only на каталог, read-write на свои таблицы).
2. Вызывает LLM-провайдера (конфигурируется, см. §7).
3. Возвращает строгий JSON, совместимый с форматом `pc_builds.components`.

## 2. Источники данных в БД (schema: `t_p72635010_quantum_fusion_resea`)

Воркер работает с уже существующими таблицами. **Ничего в них не меняет**, только читает.

### 2.1. Пул железа и наличие
- `products` — каталог: `id, name, category_id, price` (розница), `stock_qty`,
  `in_stock`, `is_archived`, `brand_id`, `warranty_months`, `specs (jsonb)`.
- `warehouse_groups` — группы: `id, product_id, name, category, price_retail, is_archived`.
- `warehouse_supplies` — партии/наличие: `group_id, qty, qty_reserved, qty_negative,
  cost_price` (закупка), `purchase_date, warranty_until`.
- **Свободный остаток** = `qty - qty_reserved - qty_negative`.
- **Маржа позиции** = `products.price - warehouse_supplies.cost_price`
  (в процентах: `(price - cost_price) / price`).

### 2.2. Характеристики и совместимость
- `product_specs` — тех. атрибуты по `product_id`:
  `component_type` (cpu, motherboard, ram, gpu, psu, case, cooling, storage, fan, other),
  `socket, mem_type, tdp_watt, has_igpu, chipset, form_factor, mem_slots, m2_slots,
  ram_form, ram_modules, ram_capacity_gb, ram_freq, gpu_length_mm, gpu_power_connector,
  psu_watt, psu_form_factor, psu_connectors (jsonb), case_form_factors (jsonb),
  max_gpu_length_mm, max_cooler_height_mm, radiator_support (jsonb), cooler_sockets (jsonb),
  cooler_type, cooler_height_mm, radiator_size, cooler_tdp_rating, storage_interface`.
- `spec_links` — правила совместимости: `from_attribute_id, to_attribute_id,
  rule (eq|gte|lte|contains), note, is_active`.
- Фронтовый эталон логики совместимости — `src/components/configurator/compatCheck.ts`
  (воркер должен воспроизвести те же проверки: socket CPU↔Mobo↔Cooler,
  form_factor Mobo↔Case, суммарный TDP ≤ psu_watt с запасом, длина GPU ≤ max_gpu_length_mm,
  высота кулера ≤ max_cooler_height_mm, mem_type CPU/Mobo↔RAM).

### 2.3. Входящие заявки
- `quiz_requests`: `id, name, phone, contact_method, budget_min, budget_max,
  answers (jsonb), extra_wishes, telegram_tag, status`.
- `quiz_questions`: `id, sort_order, title, field_type, options (jsonb), is_active`.

### 2.4. Формат результата (эталон структуры сборки)
- `pc_builds`: `components (jsonb)`, `parts_total, assembly_fee, total_price,
  sell_with_vat, lock_prices`.
- Формат одного компонента (СТРОГО как в проекте):
```json
{
  "slot": "cpu|motherboard|ram|gpu|storage|psu|case|cooling|fan|extra",
  "source": "catalog",
  "source_id": 12345,
  "name": "AMD Ryzen 9 9950X",
  "price": 39060,
  "qty": 1
}
```
- Итоговая цена (как в проекте):
  `parts_total = Σ(price*qty)`; `total = parts_total + assembly_fee`;
  если `sell_with_vat` → `round_up_250(total * 1.22)`.

## 3. Функциональные требования (эндпоинты воркера)

### 3.1. `POST /ai-build/suggest` — подобрать сборку
**Вход:**
```json
{
  "input_type": "text | quiz_request | voice_text",
  "raw_text": "нужен пк для монтажа 4к и игр, бюджет до 200к",   // если text/voice
  "quiz_request_id": 123,                                        // если quiz_request
  "budget_min": 0,
  "budget_max": 200000,
  "priority": "margin | stock | spec",   // режим приоритета, см. §4
  "variants": 1,                          // сколько вариантов вернуть (1-3)
  "constraints": {                        // опционально, жёсткие требования
    "must_brands": ["AMD"],
    "exclude_brands": [],
    "required_slots": ["cpu","motherboard","ram","psu","case","cooling"],
    "optional_slots": ["gpu","storage","fan"]
  }
}
```
**Выход:**
```json
{
  "ok": true,
  "variants": [
    {
      "title": "Игровой/монтаж 4K",
      "components": [ /* формат §2.4 */ ],
      "parts_total": 187400,
      "assembly_fee": 3500,
      "total_price": 232000,
      "priority_used": "spec",
      "margin_abs": 41200,
      "margin_pct": 0.22,
      "compat_ok": true,
      "compat_issues": [],                 // список проблем совместимости (если есть)
      "reasoning": "Короткое пояснение почему такой подбор (для менеджера)",
      "fit_score": 0.92                    // насколько попали в ТЗ (0..1)
    }
  ]
}
```
**Требования:**
- Использовать ТОЛЬКО позиции со свободным остатком > 0 (кроме режима `spec`, где
  допускается «под заказ» с пометкой `available: false`).
- Не нарушать совместимость: если LLM предложил несовместимое — воркер
  автоматически чинит (заменяет позицию) и логирует.
- Цены брать актуальные из БД, НЕ доверять ценам от LLM.

### 3.2. `POST /ai-build/feedback` — фидбек менеджера
**Вход:**
```json
{
  "suggestion_id": 555,
  "action": "accepted | edited | rejected",
  "final_components": [ /* что менеджер оставил в итоге */ ],
  "manager_note": "заменил БП на 850W, клиент просил тише"
}
```
**Поведение:** сохранить как обучающий пример (см. §5). Именно это «дообучает»
агента через RAG (примеры подмешиваются в контекст следующих подборов).

### 3.3. `POST /ai-build/voice` — голосовой ввод (из Telegram)
**Вход:** `{ "telegram_file_id": "...", "chat_id": 123, "employee_id": 7 }`
**Поведение:**
1. Скачать аудио из Telegram (Bot API `getFile` + download, токен `TELEGRAM_BOT_TOKEN`).
2. Распознать речь → текст (STT-провайдер, см. §7).
3. Распарсить текст в позиции каталога (сопоставление названий с `products`/
   `warehouse_groups` через поиск, как в `tg-bot`).
4. Вернуть черновик сборки + список нераспознанных позиций для уточнения.
**Выход:** структура как в §3.1 + `unresolved: ["4080 супер?"]`.

## 4. Режимы приоритета (ключевая фича)

Пользователь выбирает режим. Влияет на функцию ранжирования кандидатов в каждом слоте.

| Режим | Что максимизируем | Логика отбора |
|-------|-------------------|---------------|
| `margin` (макс. маржинальность) | суммарную маржу сборки | среди совместимых и попадающих в бюджет — выбирать позиции с макс. `(price-cost_price)`; не выходить за `budget_max`; ТЗ соблюдать по минимуму |
| `stock` (максимум по наличию) | использование того, что лежит на складе | приоритет позициям с большим свободным остатком и без резервов; минимизировать «под заказ»; допускать разумный компромисс по ТЗ |
| `spec` (максимум по ТЗ) | соответствие задаче клиента | лучший подбор под задачу/бюджет даже если позиция «под заказ»; наличие и маржа вторичны |

- Во всех режимах: **совместимость обязательна**, **бюджет — жёсткий потолок**
  (если задан `budget_max`).
- Возвращать поля `margin_abs/margin_pct/fit_score`, чтобы менеджер видел цену
  каждого режима.

## 5. Самообучение через RAG (без fine-tuning)

Отдельные таблицы воркера (создать миграцией, префикс `ai_`):

```sql
-- Черновики, которые агент предложил
CREATE TABLE ai_build_suggestions (
  id            serial PRIMARY KEY,
  source_type   text,           -- text|quiz_request|voice_text
  source_ref    text,           -- quiz_request_id / chat_id / null
  raw_input     text,           -- исходный текст ТЗ
  priority      text,           -- margin|stock|spec
  budget_min    numeric,
  budget_max    numeric,
  result        jsonb,          -- предложенные варианты (как в §3.1)
  created_at    timestamptz DEFAULT now()
);

-- Обучающие примеры (фидбек менеджера)
CREATE TABLE ai_build_examples (
  id            serial PRIMARY KEY,
  suggestion_id int REFERENCES ai_build_suggestions(id),
  raw_input     text,           -- запрос клиента
  priority      text,
  final_components jsonb,        -- эталонный итог (что менеджер одобрил)
  manager_note  text,
  quality       text,           -- accepted|edited|rejected
  created_at    timestamptz DEFAULT now()
);
```

**Как используется:** при новом запросе воркер находит 3–5 наиболее похожих
`ai_build_examples` (по эмбеддингу raw_input или по ключевым словам: задача, бюджет,
режим) и подмешивает их в промпт LLM как «вот так собирали похожее и это одобрили».
Чем больше одобренных примеров — тем точнее подбор. Переобучение весов НЕ требуется.

Опционально (фаза 2): pgvector для семантического поиска примеров.

## 6. Пайплайн подбора (алгоритм внутри `suggest`)

1. **Парсинг ТЗ.** LLM извлекает из `raw_text` структуру: задача (гейминг/монтаж/
   офис/CAD), бюджет, пожелания (тихий/белый/RGB/бренд), обязательные слоты.
2. **Загрузка пула.** SQL: по каждому слоту — кандидаты из `products` + `product_specs`
   + свободный остаток + `cost_price`. Фильтр: не архив, слот соответствует.
3. **Первичный отбор кандидатов.** По режиму (§4) ранжируем кандидатов в каждом слоте.
4. **Сборка варианта LLM-ом.** Отдаём LLM урезанный пул (топ-N по каждому слоту),
   похожие одобренные примеры (§5), бюджет и режим. LLM выбирает конкретные позиции.
5. **Валидация совместимости** (детерминированная, НЕ LLM): прогон по `spec_links`/
   `compatCheck`-логике. При конфликте — автозамена на ближайшего совместимого кандидата.
6. **Пересчёт цен и итогов** по актуальным данным БД (§2.4). Проверка бюджета.
7. **Сохранение** в `ai_build_suggestions`, возврат клиенту.

> ВАЖНО: цены, наличие и совместимость считает КОД (детерминированно), LLM отвечает
> только за понимание ТЗ и выбор позиций. Это защищает от «галлюцинаций» по цене/наличию.

## 7. LLM / STT провайдер (конфигурируемо)

Воркер не привязан к одному провайдеру. Через переменные окружения:
```
AI_PROVIDER = openai | deepseek | gigachat | yandex | local
AI_BASE_URL = <endpoint>            # для local/self-hosted (OpenAI-совместимый API)
AI_API_KEY  = <секрет>
AI_MODEL    = <имя модели>
STT_PROVIDER = openai_whisper | yandex | local
STT_API_KEY  = <секрет>
```
- Для `local` — OpenAI-совместимый HTTP API (например Ollama/vLLM), URL задаётся
  в `AI_BASE_URL`. Тогда данные не покидают контур.
- Модуль-адаптер `llm_client.py` инкапсулирует различия провайдеров (единый
  интерфейс `chat(messages, json_schema)` и `transcribe(audio_bytes)`).
- LLM обязан возвращать **строгий JSON по схеме** (function calling / JSON mode).

Секреты в проект добавляются как переменные окружения (в основном проекте — через
UI секретов, ключи UPPERCASE). Никогда не хардкодить.

## 8. Интеграция с основным проектом

### 8.1. UI (React, добавляется в проект отдельной задачей — вне воркера)
- Кнопка **«Собрать с ИИ»** в двух местах:
  - в разделе заявок (`quiz_requests`) — по заявке;
  - на отдельной странице/модалке «Вставить текст ТЗ» — свободный текст.
- Переключатель режима: **Макс. маржинальность / Максимум по наличию / Максимум по ТЗ**.
- Экран результата: список позиций (как в конфигураторе), итог, маржа, fit_score,
  предупреждения совместимости; кнопки **Принять / Править / Отклонить** → `feedback`.
- «Принять» → создать `pc_builds` (status=wip) через существующий `backend/builds`.

### 8.2. Telegram голос (в существующий `backend/tg-bot`)
- Добавить обработку `message.voice` в webhook → вызвать `/ai-build/voice`.
- Привязка `telegram_id → employee` (сборщик) — использовать существующую логику
  идентификации бота / `tg_bot_managers`.

### 8.3. Контракты (URL функций основного проекта — из func2url.json)
- Каталог/наличие читаются напрямую из БД воркером (быстрее и без лишних вызовов).
- Создание сборки — через `backend/builds` (action создания) ЛИБО прямой INSERT
  в `pc_builds` по согласованию. Предпочтительно через существующую функцию, чтобы
  не дублировать логику цен (`lock_prices`, НДС).

## 9. Нефункциональные требования
- **Детерминированность цен/наличия/совместимости** — только из БД, не из LLM.
- **Идемпотентность** — повтор `suggest` с тем же входом не плодит мусор
  (или помечать пересоздание).
- **Таймауты** — подбор ≤ 30 c; голос ≤ 60 c.
- **Логи** — сохранять запрос/ответ LLM в `ai_build_suggestions.result` для аудита.
- **Приватность** — для `local` провайдера ни один байт данных не уходит наружу.
- **Обезличивание** — при облачном провайдере не отправлять ФИО/телефон клиента в LLM
  (только суть ТЗ, бюджет, пожелания).
- **Безопасность SQL** — Simple Query Protocol, экранирование строк (как в проекте).

## 10. Этапы (roadmap)
1. **MVP-1 (подбор по тексту):** `suggest` (режим `spec`) + валидация совместимости +
   пересчёт цен. UI «Вставить текст ТЗ» → черновик.
2. **MVP-2 (режимы):** добавить `margin` и `stock`, поля маржи/fit_score.
3. **MVP-3 (заявки):** вход `quiz_request`, кнопка «Собрать с ИИ» в заявках.
4. **MVP-4 (обучение):** `feedback` + `ai_build_examples` + подмешивание примеров.
5. **MVP-5 (голос):** `voice` + Telegram webhook voice + STT.
6. **Фаза 2:** pgvector для примеров; переезд на локальную модель (`AI_PROVIDER=local`).

## 11. Критерии приёмки (Definition of Done)
- [ ] По свободному тексту ТЗ возвращается совместимая сборка в пределах бюджета.
- [ ] Три режима дают ощутимо разные результаты (маржа/наличие/ТЗ).
- [ ] Ни одна возвращённая сборка не нарушает правил `spec_links`.
- [ ] Все цены/итоги совпадают с расчётом основного проекта (НДС, assembly_fee).
- [ ] Фидбек менеджера сохраняется и влияет на последующие подборы.
- [ ] Голосовое из Telegram превращается в черновик сборки.
- [ ] Локальный провайдер (`AI_PROVIDER=local`) работает без утечки данных наружу.
