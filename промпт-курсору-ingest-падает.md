# Задача для Cursor: чинить отправку результатов (ingest) из StressRunner

## Симптом
После прогона EXE пишет:
```
Метрики собраны: 49 показателей.
Отправляю результат на сайт...
Не удалось отправить (сохранено локально).
```
При этом **уведомление в Telegram приходит** («Прогон завершён»).

## Диагностика (уже проведена на стороне сайта)
- Запрос `notify` (POST `?action=notify`) **доходит** до cloud-функции и отрабатывает —
  значит URL, токен `X-Stress-Token` и сеть РАБОТАЮТ.
- Запрос `ingest` (POST `?action=ingest`) **в логах cloud-функции ОТСУТСТВУЕТ** —
  его не видно вообще. То есть он **не доходит до сервера** (не доходит до выполнения
  обработчика). Значит ошибка возникает на стороне EXE: либо при формировании тела,
  либо запрос отбивается транспортом/прокси ещё до функции.

## Наиболее вероятная причина: РАЗМЕР ТЕЛА запроса со скриншотом

В этом прогоне есть тест в режиме `screenshot` (FurMark + GPU-Z) — EXE прикладывает
PNG-скриншот как base64 внутри JSON (`results[].files[].content_base64`). 

- PNG-скриншот экрана FullHD/4K в base64 = **несколько МБ** (часто 3–10 МБ).
- У облачной функции есть лимит на размер тела входящего запроса (порядка **~6 МБ**).
  Если тело больше лимита — платформа/шлюз отбрасывает запрос **ДО** функции,
  поэтому в логах его нет, а EXE получает ошибку соединения → «сохранено локально».
- `notify` — крошечный JSON, поэтому проходит всегда. Это объясняет, почему
  уведомление есть, а отчёта нет.

## Что нужно сделать в EXE (Cursor)

### 1. Логировать РЕАЛЬНУЮ причину ошибки ingest (сейчас она глотается)
Сейчас любое исключение превращается в «Не удалось отправить (сохранено локально)».
Нужно при ошибке выводить/логировать:
- HTTP статус-код ответа (если ответ был);
- тело ответа сервера (если есть);
- текст исключения (`ex.Message`, для HttpRequestException — InnerException);
- **размер тела запроса в байтах** (критично для диагностики лимита).

Пример (C#):
```csharp
var bytes = Encoding.UTF8.GetByteCount(jsonBody);
Console.WriteLine($"ingest: размер тела = {bytes/1024.0/1024.0:F2} МБ");
try {
    var resp = await http.PostAsync(url, content);
    var respText = await resp.Content.ReadAsStringAsync();
    Console.WriteLine($"ingest: HTTP {(int)resp.StatusCode}, ответ: {respText}");
    resp.EnsureSuccessStatusCode();
} catch (Exception ex) {
    Console.WriteLine($"ingest ОШИБКА: {ex.GetType().Name}: {ex.Message}");
    if (ex.InnerException != null) Console.WriteLine($"  inner: {ex.InnerException.Message}");
    // сохранить локально как сейчас
}
```

### 2. Уменьшить размер скриншотов перед отправкой (ГЛАВНОЕ)
Скриншот должен влезать в лимит тела. Сделать одно из (лучше всё):
- **Сжимать в JPEG с качеством ~70–80** вместо PNG (PNG скриншота огромный).
  Имя файла — `*.jpg`, тогда сайт корректно покажет как изображение.
- **Уменьшать разрешение** длинной стороны до ~1600 px (для чтения показаний GPU-Z
  этого с запасом хватает).
- Ориентир: итоговый файл скриншота — **не более ~1.5 МБ**, а суммарное тело
  запроса ingest — **до ~5 МБ** с запасом под лимит.

Пример сжатия (C#, System.Drawing / ImageSharp):
```csharp
// JPEG quality 75, ресайз до 1600px по длинной стороне
```

### 3. Подстраховка: если файлы делают тело слишком большим — слать ingest БЕЗ файлов,
а файлы догружать отдельным механизмом НЕ нужно (не усложняем). Достаточно п.2:
ужать скриншот так, чтобы тело гарантированно влезало. Контракт менять НЕ нужно —
формат `results[].files[].content_base64` остаётся прежним, просто файл меньше.

### 4. Проверить таймаут HttpClient в EXE
Тело с картинкой грузится дольше. Поставить таймаут запроса ingest **60–120 секунд**
(не дефолтные 100 c HttpClient, а явно, и убедиться, что не меньше).

## Контракт (НЕ меняется)
- Эндпоинт: `POST {BASE_URL}?action=ingest`, заголовок `X-Stress-Token`.
- Тело — JSON как в `документация-стресс-тесты.md` §4.
- Скриншоты — внутри `results[].files[]`: `{ "name": "shot.jpg", "content_base64": "<...>" }`.
- Идемпотентность по `run_uid` — при ретрае слать ТОТ ЖЕ `run_uid`.

## Как проверить, что починилось
1. Запустить прогон с тестом-скриншотом.
2. В консоли EXE должен появиться лог: `ingest: размер тела = X МБ` и `HTTP 200`.
3. На сайте `/admin/stress` прогон появится в списке, в карточке — превью скриншота
   (сайт уже умеет показывать image/* как картинку).

## Ожидаемый ответ сервера при успехе
```json
{ "ok": true, "run_id": 123, "results": 1, "metrics": 49 }
```
Если приходит этот JSON — всё хорошо, отчёт на сайте появится.

## Примечание для координации (сторона сайта уже сделала)
- S3-клиент кэшируется, ContentType по расширению (png/jpg → image/*), приём
  `metrics[]`, отдача в админке. Менять сайт под эту задачу НЕ требуется —
  фикс полностью на стороне EXE (размер тела/скриншота + логирование причины).
